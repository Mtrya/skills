# 演示文稿工作流

核心思路：**不直接碰 OOXML**。用 YAML 中间格式 `.pptd` 描述演示文稿——每页自包含、人可直接读写——再用脚本校验和导出。先读 [pptd-spec.md](pptd-spec.md) 掌握格式与本地支持范围，再按下面的流程工作。

## 五步工作流

### 第 1 步：读透上下文
读完用户提供的所有信息：上传文件、提到的 URL、其他背景。有文档读文档，有参考读参考，不要只读一半就开写。

### 第 2 步：判定三个维度

**请求类型**
- 新建：从零或基于模板创建
- 编辑：改用户上传的 PPT（局部修改、单页美化）——先把 pptx 解包或用 python-pptx 读懂结构再改
- 复刻：把图片/PDF 等复刻成 PPT——尽量 1:1，难辨认处用网格线、局部放大辅助

**设计方式**
- 自主设计：无偏好或只有简单风格约束 → 读 [design-playbook.md](design-playbook.md)，按场景分类设计
- 设计系统：用户给了完整设计规范 → 严格遵守，严禁混入其他风格
- 使用模板：用户给了模板 pptx → 截图分析其视觉语言（配色、字体、版式、组件），提取封面/目录/章节页/正文的母版规律后仿写
- 风格迁移：给了参考图/网页 → 分析视觉特征后借用，鼓励复用原图的字体层级和元素

**输入类型**
- 只有主题：需自行扩展内容 → 用搜索补充材料、案例、数据
- 完整文档：按文档组织内容
- 逐页大纲/讲稿：页数匹配大纲
- 文档或大纲未说明能否扩展时：默认**可以搜索扩展**，除非用户明说不要

**页数**
- 用户指定 → 以用户为准
- 大纲/讲稿 → 匹配大纲页数
- 只有主题或完整文档 → 用 ask 工具确认页数（给出推荐值）

以下情况必须先问清楚再动手：意图模糊、文件打不开、需求自相矛盾（如"10 页"和"30+ 页"并存）、设计风格之间冲突（如麦肯锡风 vs 大面积留白）。

### 第 3 步：生成

**图片使用规范**
1. 图片不只用于封面和章节页——正文页也要用图来丰富版面、帮助理解、支撑决策。
2. 图片的作用：展示具体对象、解释内容、提供证据、建立场景。logo、图标、装饰纹理不算实质图片。
3. 页面涉及产品、人物、地点、建筑、事件、案例、界面、实验对象时，优先真实图片或截图，实在没有再用生成图。
4. 优先级：用户提供 > 官网/官方报告 > 搜索所得相关图 > 生成图。
5. 决定用哪些图后，先批量完成搜索/生成/下载，再围绕图片比例设计页面。图存 `media/` 目录，保持清晰，绝不拉伸变形。
6. 分析、技术、学术类 PPT，有产品、实验、界面、案例材料时必须有对应证据图；不许把每页都做成文字+色块。
7. 不为凑数加无关图——每张图必须直接服务于本页结论。

**内容准则**
- 避免抽象表达和生僻比喻；不用"赋能、闭环、抓手、N 步论证、一目了然"这类口号式词汇。
- 不用 AI 常见句式："不是 X，而是 Y"、"X 就是 Y"、"关键在于"、"N 条战线/路径"。
- 不用过度口语："弹药往哪打"、"第 N 件事"、"没法当 X 用"。

### 第 4 步：校验

1. 跑 `python scripts/pptd_check.py <目录>`，多轮修复。
   - 校验器检查格式和导出支持范围；溢出、遮挡与字体替换需通过渲染检查。
   - 刻意出血产生的 BoundsOutside 可按实际设计判断；Unsupported 必须处理后才能导出。
2. 导出 pptx 转图检查视觉，发现问题改 .page 文件再校验，循环到干净为止。

### 第 5 步：交付

交付 `.pptd` 源文件目录（打包）和导出的 `.pptx`。告诉用户：pptx 可直接用；要改内容就改对应 `.page` 文件后重新导出。

## 重要规则

1. 产物写在用户指定位置或项目已有输出目录，多文件结构：主入口 `xxx.pptd` + `pages/page-N.page` + `media/`。
2. 动画只在用户明确要求，或明显用于现场演讲且动画有助于分步揭示、流程演示、因果解释时使用；阅读型、自学型、打印型一律不加。本地导出器不支持动画，确有需要时使用支持该能力的工具编辑成品。
3. 演讲者备注只在用户明确要求时添加；本地导出器不处理备注，需在成品中添加并核对。
4. 制作时尽量并行写多个 .page 文件，减少轮次。
5. 尺寸默认 16:9 = [960, 540]；用户要求 4:3 时用 [960, 720]。
