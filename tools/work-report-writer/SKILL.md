# 周报 / 月报生成器

输入是碎片（笔记、聊天记录、口头描述、git 提交），输出是让领导 30 秒看懂、5 分钟读完的报告。按以下流程执行。

## 第一步：收集两类信息

**1. 工作记录（问用户要，缺项可跳过）**
- 本周期完成的主要事项
- 进行中未完成的事项
- 遇到的问题或阻塞
- 下周期计划
- 关键数据或指标（如有）

任何形式都行：散乱笔记、待办清单截图、语音转文字。碎片不是问题，碎片正是这个技能存在的理由。

**2. Git 提交记录（自动获取）**

若工作目录是 git 仓库且用户没有明确说不需要：

```bash
GIT_USER=$(git config user.name)
# 周报（近 7 天）
git log --since="7 days ago" --author="$GIT_USER" --pretty=format:"%h %s (%ai)" --no-merges
# 月报（近 30 天）
git log --since="30 days ago" --author="$GIT_USER" --pretty=format:"%h %s (%ai)" --no-merges
```

用户指定了时间范围或作者就替换参数。不是 git 仓库就跳过，不要硬凑。

## 第二步：确认报告参数

用户初始请求里已明确的不再问。缺失的用一次提问全部确认：

| 参数 | 选项 | 默认 |
|---|---|---|
| 报告类型 | 周报 / 月报 | 周报 |
| 风格 | 数据导向 / 叙事型 / OKR 对齐 | 数据导向 |
| 时间范围 | 自定义 | 近 7 天 / 近 30 天 |
| 语言 | 中文 / 英文 | 中文 |
| 汇报对象 | 直属领导 / 团队 / 跨部门 | 直属领导 |

## 第三步：整理归类

所有信息归入五个桶：

1. **已完成**——本周期交付的
2. **进行中**——附进度百分比估算
3. **问题与风险**——阻塞、延期、外部依赖
4. **下期计划**——下周期的重点
5. **关键数据**——量化指标（如有）

Git 提交按**功能模块/工作事项聚合**，不逐条罗列。八个修同一个功能的 commit 合并成一句："重构了 XX 模块的 XX 逻辑"。

## 第四步：按风格生成

### 风格一：数据导向
强调数字、完成率、对比。适合要量化成果的场景。

### 风格二：叙事型
适合非技术背景的领导，或需要传达背景和价值的场景。

### 风格三：OKR 对齐
适合 OKR 驱动的团队，把工作映射到目标和关键结果。

## 生成规范（三种风格通用）

1. **去碎片化**：相关小事项合并为一个主题，拒绝流水账。
2. **量化优先**：能用数字就不用形容词——完成数量、进度百分比、指标变化。
3. **区分事实与计划**：完成的用过去时，进行中的标进度，计划中的标预期时间。
4. **突出价值**：每项工作关联业务价值或项目目标，不只描述动作。"优化了接口"不如"接口耗时从 800ms 降到 200ms，投诉工单预计减少一半"。
5. **风险前置**：有阻塞先说，别埋在细节里等领导发现。
6. **语言简洁**：每事项 1–2 句话。

## 输出要求

- Markdown 格式，直接输出到对话供复制；用户要求存文件则写入指定路径。
- 标题中明确标注时间范围。
- 写完自查：删掉所有没有信息量的句子（"本周工作比较充实"之类），逐条核对数字是否与原始记录一致。
